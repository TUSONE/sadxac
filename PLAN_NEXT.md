# Славик: план стабилизации и передача следующей модели

Дата: 12 октября 2026. Основа кода: `f031a50` в `TUSONE/sadxac`, ветка `main`.
Этот документ подготовлен по истории чата, архиву handoff и проверке текущего кода.
На этом шаге пользователь попросил анализ и план, затем продолжение с другой моделью.
Изменения поведения из этого плана ещё не реализованы. 43 локальных теста предыдущей
версии не подтверждают качество звука, распознавания или управления на плате.

## 1. Что пользователь хочет получить

- Одна аккуратная установка от `tusone` в `~/slavik`, без новых файлов агента в `/root`.
- Обновления через GitHub: скачивание архивов пользователю неудобно. Публикация в
  `TUSONE/sadxac/main` ранее явно разрешена. Старые root-файлы не удалять.
- Непрерывный Live: микрофон и сессия открыты, без переподключения на каждую фразу.
- Настоящее перебивание голосом во время ответа; ассистент не перебивает сам себя.
- Обращения «Славик», «Славка», «Эй Славка», «Славуха»; исторически также
  «Ебаные славики». Имя может стоять в любой части предложения:
  «Славка, как дела?», «Как дела, Славка?», «Включи, Славка, музыку».
- После обращения короткое окно команд без повторения имени; после 5 секунд
  бездействия — тишина до следующего обращения. Фоновая речь не должна снова будить.
- Хорошая калибровка и понятная русская/английская речь, без случайного переключения
  на другие языки и без выдумывания команд из шума.
- Максимальный чистый уровень выхода платы. Общая громкость регулируется ручкой
  колонки и голосом; отдельная громкость Spotify допустима, но уровни должны быть понятны.
- Spotify: выбор произвольного трека в приложении и голосом, следующий/предыдущий,
  пауза/продолжение, песня/исполнитель/плейлист по названию, выбор внутри плейлиста
  с сохранением очереди, музыка по настроению («грустная», «для работы» и т. п.).
- Лёгкая реализация для Banana Pi с ~484 МБ RAM, без тяжёлого локального ASR по умолчанию.

## 3. Текущая архитектура и код

- `gemini_assistant_dialog.py`: Live, receive-loop, WakeGate, очередь/flush,
  ресемплинг, калибровка/диагностика CLI, объявления инструментов.
- `mic_processing.py`: HP 60 Hz, фиксированный gain, ограничитель пиков,
  калибровка по тишине/речи; измеряет оба канала, использует правый.
- `slavik-audio`: root-owned ограниченный мост, запускаемый как `voice`;
  capture/playback/check/volume. Устанавливается через `install-linux.sh` с sudoers.
- `spotify_api.py`: OAuth, refresh, поиск, управление конкретным устройством,
  чтение плейлиста и воспроизведение с context_uri/offset.
- `slavik-spotify-player`: supervisor librespot; native Pulse предпочтителен,
  fallback decoded S16 stereo 44100 → pacat → AEC. Это отдельный формат Spotify,
  его нельзя механически заменять на частоту Gemini.
- `install-spotify-connect.sh`: systemd-служба от `voice`, кэш/временный каталог.
- `set-output-max.sh`: ALSA Headphone/Speaker/Playback 100%, PCM on,
  физический Pulse sink и AEC sink 100%, backup и alsactl store.

Контракт Gemini: PCM16 16k stereo из AEC → **правый** mono в Gemini;
PCM16 mono 24k от Gemini → ресемплинг 48k → stereo → AEC sink.
`response.data` имеет приоритет, inline PCM — fallback. Сейчас ветка response.data
жёстко считает частоту 24k; в диагностике следует читать/сопоставлять MIME-метаданные,
но это не доказанная причина текущих провалов. Не дублировать одни аудиобайты дважды.

Wake пока зависит от серверной input transcription. Это выходной фильтр, а не
локальный детектор имени. Фоновый звук всё равно попадает в Gemini. RU/EN language_codes
являются подсказками, не строгой языковой блокировкой. При явном отклонении поля
в setup есть fallback без него. Модель понимает исходное аудио, текст транскрипции
не является безошибочным представлением того, что она услышала.

В f031a50 добавлены: отдельное «Славка», имя в любой позиции, общая громкость через
AEC sink, play_from_playlist, play_mood, поиск своих плейлистов, новые OAuth scopes.
VAD: START LOW, END LOW, prefix 500 ms, silence 700 ms. Начальная громкость librespot
изменена с 35 на 100. Эти изменения могли изменить акустические условия; фактические
значения и успешное применение на плате нужно снять, а не предполагать.

## 4. Последний отчёт: факты и гипотезы

Факты из лога пользователя:

- `gain=0.5171`, `SNR=24.0dB`; соединение Live успешно, окно 5s.
- Иногда «Привет, Славик» распознаётся правильно и получается ответ.
- Часто появляются `[Перебивание: звук очищен]`.
- В коде каждое `server_content.interrupted` вызывает flush очереди и остановку
  pacat: эти события точно могут обрывать ответ. Причина серверного interruption неизвестна.
- После «Повтори, пожалуйста» от ассистента появился ввод «Повторите. Пожалуйста».
- Имя распознаётся как «Swipe», «Парик», «Слай», «старик», «Сладко», «Слуха»;
  встречаются немецкая и японская транскрипции.
- По словам пользователя, Spotify играет первый трек плейлиста и не позволяет
  вручную выбрать другой. Неизвестно, не переключается ли он вообще или переключается
  и возвращается на первый; источник ручной команды и версия клиента тоже не уточнены.

Приоритетные гипотезы:

1. Утечка звука колонки в микрофон / недостаточное AEC / неверная reference-маршрутизация.
   Похожая входная фраза после собственного ответа — сильный признак, но не доказательство.
2. Перегрузка аналогового тракта или изменение акустики после выставления 100%.
   AEC плохо устраняет нелинейные искажения. 100% не обязательно означает unity gain.
3. Dropout/underrun PipeWire, перегрузка CPU, захват/сеть — проверить метриками;
   дробная печать output transcription сама по себе не доказывает провалы аудио.
4. Плохое имя — частично следствие плохого аудио и зависимости wake от транскрипции.
   Массовое добавление «старик», «сладко» и похожих слов создаст ложные пробуждения.
5. Spotify: проблема Connect/очереди/команд другого клиента либо повторного play.
   Начинать плейлист с первого трека без offset нормально; невозможность ручного
   выбора — отдельный дефект. Он не исправлен одними новыми голосовыми инструментами.

`gain=0.5171` — примерно −5.7 dB программного ослабления. Это не доказательство,
что микрофон слишком тихий: калибровка могла ограничить пики. SNR 24 dB измерялся
при калибровке и ничего не доказывает об эхе во время музыки/ответа. Нельзя просто
поднять gain до 4 или отключить AEC и объявить проблему решённой.

## 5. План работ по порядку

### Этап A. Воспроизводимость и диагностика без изменения настроек

1. Получить `git rev-parse --short HEAD` платы, версии librespot/PipeWire,
   текущее состояние микшера, AEC-модулей и маршрутов. Не читать/публиковать `.env`
   и spotify-token.json целиком. Подтвердить единственный агент и единственный Connect.
2. Добавить компактный `--diagnose` или отдельный сборщик: версии, устройства,
   частоты/каналы/уровни, состояние сервисов, счётчики очереди/отброшенных кадров,
   метки времени interruption и tool call/result. Без ключей, OAuth URL с кодами,
   токенов и без записи разговоров по умолчанию.
3. Проверить три сценария отдельно: только звук без Gemini; Gemini в тишине;
   Gemini с музыкой. На каждом фиксировать слышимый результат и логи.
4. Проверить CPU/RAM/underrun во время нагрузки, а не по idle-показателям.

Готово, когда конкретный провал можно связать с interruption, сбоем плеера,
истощением/задержкой буфера или ошибкой устройства. Не менять всё одновременно.

### Этап B. AEC, вход и громкость

1. Убедиться, что и Gemini, и Spotify идут в один `voice_aec_sink`, а source AEC
   слушает правильную физическую карту; нет обходного воспроизведения в физический sink.
   Старый конфиг архива задаёт WebRTC AEC 48000/2; наличие имён узлов не доказывает,
   что reference/source сейчас правильно соединены.
2. Проверить тишину, человеческую речь без вывода, собственный голос и музыку без
   человеческой речи. Сравнить уровни/клиппинг до и после AEC, оба входных канала.
   Правый канал не менять без измерений и прослушивания тестовой фразы пользователем.
3. Выстроить уровни: максимальный **неискажённый** выход платы, затем программный
   master 0..100% для голоса и музыки. Не смешивать аналоговый boost, цифровой Playback,
   громкость физического sink, AEC sink, отдельный Spotify и ручку колонки.
4. Проверить новую калибровку с запасом по пикам и устойчивостью к одиночному шуму.
   Сравнить текущий профиль с gain=1 при одинаковой фразе, а не просто повысить усиление.
5. Только если нужны — точечные изменения AEC/буферов, с резервной копией конфигов,
   проверкой после каждого изменения и конкретным откатом.

Готово: 10 последовательных ответов без самообрыва; при молчании человека собственный
голос не запускает wake/команды; реальное перебивание всё ещё останавливает ответ.
Не лечить самоэхо выключением микрофона и не игнорировать все interruption-события.

### Этап C. Spotify отдельно от Gemini

1. Остановить только агент Ctrl+C, оставить slavik-spotify. В приложении Spotify
   выбрать именно `Slavik`, затем 1-й, 3-й и 2-й трек одного плейлиста, next/previous,
   другой альбом/плейлист. Записать, остаётся ли старый трек или возвращается первый.
2. Одновременно собрать `journalctl -u slavik-spotify --since "5 minutes ago"`.
   Проверить restart count, ошибки потока/сети/декодера/временного каталога, активные
   raspotify/librespot/spotifyd, другой клиент, shuffle/repeat и ограничения аккаунта.
   Не удалять cache/token и не переустанавливать службы без причины.
3. Расширить --spotify-status: активное устройство, restricted/supports_volume,
   текущий трек, context, progress_ms, repeat/shuffle, действия из disallows.
   Снять состояние до/после ручного выбора. Секреты не выводить.
4. Если ручное переключение работает без агента — логировать голосовые tool calls,
   проверить повторный play_playlist, его авторизацию и поведение при interruption.
   В текущем коде уже поставленная в очередь команда не отменяется автоматически
   по tool_call_cancellation. Проверить актуальный SDK и добавить корректную отмену
   ещё не выполненных команд/защиту от повторной обработки идентичного call id.
   Выполненный внешний запрос нельзя считать отменённым задним числом.
5. Только после исправления Connect проверить API-команды и голосовое отображение:
   track, artist, playlist, mood, next, previous, pause/resume, номер/название внутри
   плейлиста. context_uri/offset сохраняют очередь; одиночный uris:[track] заменяет её.
6. Проверить актуальные ограничения Spotify API для этого приложения и аккаунта.
   Закрытые плейлисты требуют повторного OAuth с добавленными scopes. Отсутствие
   прав чтения нельзя маскировать успешным выбором песни; подбор по настроению
   сейчас поиск плейлистов, а не API recommendations и не гарантированная персонализация.

Готово: ручной и голосовой выбор любых трёх песен работает и не возвращает первый;
next/previous сохраняют нужный контекст, ошибки API сообщаются честно.

### Этап D. Распознавание, wake и таймер

1. После чистого аудио проверить стандартный набор RU/EN фраз на одной дистанции,
   с музыкой и без. Сохранить таблицу: произнесено → транскрипция → пробуждение → действие.
2. Проверить реальные language_codes/модель/API, не обещать жёсткий RU/EN allowlist.
   Системная инструкция регулирует ответы, но не исправляет микрофон. Возможный
   русский приоритет оценивать сравнением, с проверкой английских названий песен.
3. Исправлять только наблюдённые безопасные варианты имени. Не включать широкий
   fuzzy-match по фоновым словам. Если серверный wake остаётся ненадёжным, отдельным
   небольшим прототипом оценить детектор ключевого слова с поддержкой русского и
   реальными бюджетами CPU/RAM. Не ставить большой Whisper/Vosk без замеров/решения.
4. Формализовать состояния: спит → слушает команду → выполняет/отвечает → ждёт.
   Рекомендуемая UX-семантика: полные 5 секунд ожидания следующей команды после
   окончания слышимого ответа, продление по речи пользователя, не по собственной.
   Сейчас deadline считается от input transcription; за длинным ответом он может
   истечь. Это предложение уточняет прежнее требование, ещё не утверждённая реализация.
5. Имя в конце должно авторизовать всю текущую фразу; при этом нельзя выпускать
   старый ответ на фоновую речь. Нужны тесты границ input turn, поздней транскрипции,
   таймера и асинхронных tool calls, а не просто поиск подстроки в одном событии.

Готово: минимум 9/10 пробуждений для имени в каждой позиции в тишине; отдельно
зафиксированный результат с музыкой; 5 минут фона без ложных команд. Это цели
приёмки, а не уже достигнутые результаты. Пять секунд тишины возвращают сон.

### Этап E. Надёжность, тесты, публикация

- Точечные тесты PCM/метаданных без двойного воспроизведения, очереди/flush,
  wake/таймера/границ реплик, volume и Spotify context/cancellation/errors.
- Обработать сетевой обрыв/лимит Live с поддерживаемым восстановлением сессии,
  если проверка подтвердит необходимость. Не переподключаться на каждую фразу.
- Один небольшой commit на проверенную причину. Обновлять README, VALIDATION,
  SHA256SUMS; публиковать в GitHub и давать короткие команды обновления/отката.
- Проверить на плате 15 минут с музыкой, командами и перебиваниями; повторить после
  перезагрузки. Локальные unit-тесты не заменяют этот этап.

## Прогресс диагностики после передачи

Пользователь проверил ручной выбор 1-го/3-го/2-го трека при остановленном
Gemini: остаётся прежний трек. Значит сбой воспроизводится без голосового агента.
Добавлены --diagnose, подробный --spotify-status, --spotify-next/--spotify-previous
для проверки API отдельно от приложения и SLAVIK_DEBUG_EVENTS=1 для событий Live.
Настройки звука и поведение interruption пока не изменены. Следующий шаг — сравнить
состояние Spotify и журнал службы после ручного выбора и API next, затем проверить
фактические AEC source/sink/master и уровни по снимку.

## 6. Первые действия следующей модели

Не начинать с переписывания агента. Прочитать этот файл и соответствующие участки
кода. Пользователь не обязан снова пересказывать историю. Сначала собрать минимальные
данные и выполнить изоляцию Spotify без Gemini. Команды для пользователя:

```bash
cd ~/slavik
git rev-parse --short HEAD
/usr/bin/librespot --version
sudo systemctl show slavik-spotify -p ActiveState -p SubState -p NRestarts
sudo journalctl -u slavik-spotify --since '5 minutes ago' --no-pager
voice_uid=$(id -u voice)
sudo -u voice env XDG_RUNTIME_DIR="/run/user/$voice_uid" \
  PULSE_SERVER="unix:/run/user/$voice_uid/pulse/native" pactl list short modules
sudo -u voice env XDG_RUNTIME_DIR="/run/user/$voice_uid" \
```

https://github.com/PipeWire/pipewire/blob/1.4.2/src/modules/module-echo-cancel.c
https://github.com/PipeWire/pipewire/blob/1.4.2/src/modules/module-protocol-pulse/modules/module-echo-cancel.c
process() берёт size=impl->aec_blocksize, отдаёт один блок playback и сбрасывает
sink_ready/capture_ready; callbacks вызывают его один раз, без цикла обработки
оставшихся входных блоков. Pulse-обёртка не передаёт общий node.latency; по умолчанию
WebRTC latency10мс, значит aec_blocksize480 при48кГц (видно также в pw-top).
Принудительный цикл960 при сохранении внутреннего блока480 не обеспечивает полный
выход на каждом цикле. Предыдущая гипотеза о достаточности кратности была неверной.

Исправление: остановить агента, git pull, bash repair-aec.sh. Скрипт ставит runtime
quantum480 (10мс), пересоздаёт Pulse/AEC через restart pipewire-pulse пользователяvoice,
проверяет появление AEC nodes и перезапускает slavik-spotify для подключения к новым
узлам. Музыка кратко прекращается. Системный PipeWire не рестартуется, metadata480
остаётся. Бывшие уровни/калибровка могут потребовать проверки после перезапуска Pulse;
намеренно не добавлены новые изменения микшера. Исходный force-quantum сохранён старым
backup-механизмом, audio-buffer.sh restore возвращает его. Не применять960/1024 с этим
AEC без одновременного изменения внутреннего размера блока или реализации модуля.

Приёмка ещё нужна: граф480, речь/музыка без роботизации и отсутствие роста ERR на
ВСЕХ узлах. Если на480 проявится нехватка времени, следующим шагом исправлять RT
доступ/планирование либо менять реализацию AEC с согласованным размером блока, а не
снова увеличивать только quantum. Ввод на50см ещё не оценён по WAV; усиление не трогать.
